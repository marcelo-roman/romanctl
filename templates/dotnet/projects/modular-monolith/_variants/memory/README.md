# SampleApp

.NET API as a modular monolith with DDD, generated by `romanctl`.

```bash
romanctl run sample-app
dotnet test
```

Address: http://localhost:5083. OpenAPI document: `/openapi/v1.json`.

## Modules

A single process and a single deploy, with the code split into modules that cannot see each other's internals.
Each module has two projects:

| Project | Contents |
|---|---|
| `SampleApp.<Module>` | The implementation, all `internal`: `Domain`, `Application`, `Infrastructure`, `Endpoints` and the registration in `<Module>Module.cs` |
| `SampleApp.<Module>.Contracts` | What other modules may use: query interfaces and integration events |

| Module | Routes | Schema |
|---|---|---|
| `Catalog` | `POST /catalog/products`, `GET /catalog/products/{id}`, `GET /catalog/products?limit=` | `catalog` |
| `Ordering` | `POST /orders`, `POST /orders/{id}/items`, `POST /orders/{id}/place`, `GET /orders/{id}`, `GET /orders?limit=` | `ordering` |

`SampleApp.Shared` holds the minimum everyone uses: `Money`, `DomainException`, the in-process event bus, error
handling as ProblemDetails and the registration of one `DbContext` per module.
`SampleApp.Api` only composes the modules, in `Modules.cs`.

## How the modules talk

- **Synchronous query through a contract.** To add an item, `Ordering` asks `ICatalogApi`, from
  `SampleApp.Catalog.Contracts`, for the product and gets back a `ProductSnapshot` with name and price. It never touches `Product`
  nor the catalog data.
- **Asynchronous integration event.** When the order is placed, `Ordering` publishes `OrderPlaced`, from
  `SampleApp.Ordering.Contracts`, on the `IEventBus`. The event goes into an in-memory queue and is delivered outside the
  request, in its own scope, to each `IIntegrationEventHandler<OrderPlaced>`. `Catalog` handles the event and
  adds up the sold quantity of each product (`soldQuantity`).

The queue is in memory: an event that was published and not yet handled is lost if the process stops.

The architecture tests, with NetArchTest, ensure that a module only uses the contracts of the others, that contracts
depend on no implementation or framework, that `Shared` knows no module and that the domain of
each module does not depend on the other layers.

The rules live in the domain; the endpoints only translate HTTP. An invalid body returns 400, a violated rule returns 422
and an unknown resource returns 404, always as ProblemDetails.

## Persistence

In memory, with the EF Core InMemory provider and one `DbContext` per module: the data is gone when the API stops.
To use PostgreSQL, with one schema per module, generate the project with `--with postgres`.

## Generate code

```bash
romanctl add module Shipment                  # Shipments module with the Shipment entity: contracts, routes and tests
romanctl add resource Category --in Catalog   # entity with CRUD inside an existing module
```
