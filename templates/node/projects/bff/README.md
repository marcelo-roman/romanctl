# SampleApp

Node monorepo with the Backend for Frontend pattern, generated by `romanctl`: an orders API, a BFF and a React web
app, each one in its own program.

```bash
romanctl up sample-app
npm test
```

| Program | Folder | Address | What it is |
|---|---|---|---|
| `web` | `apps/web` | http://localhost:3300 | React SPA with Vite; talks only to the BFF |
| `bff` | `apps/bff` | http://localhost:3301 | Fastify; builds the web screens from the API |
| `api` | `apps/api` | http://localhost:3302 | Fastify; orders and catalog, with the business rules |

`romanctl run` and `romanctl up` start the three together, with `[api]`, `[bff]` and `[web]` at the start of each log
line. Without `romanctl`, `npm run dev` at the root does the same.

| Root script | What it does |
|---|---|
| `npm run dev` | Starts the API, the BFF and the web app |
| `npm test` | Checks the types and runs the tests of every program and the architecture test |
| `npm run build` | Compiles the API and the BFF to `dist/` and builds the static web app in `apps/web/dist` |

| Variable | Read by | Default |
|---|---|---|
| `API_PORT` | api | `3302` |
| `DATABASE_URL` | api | `postgres://postgres:postgres@127.0.0.1:5432/sample_app` |
| `BFF_PORT` | bff | `3301` |
| `API_URL` | bff | `http://localhost:3302` |
| `WEB_DIST` | bff | none; with a folder, the BFF also serves the compiled web app |
| `BFF_URL` | web, in `vite` | `http://localhost:3301` |

## Backend for Frontend

The web app does not know the API. It asks the BFF for ready-made screens, and the BFF calls the API, joins and
formats what the screen needs:

| Method | BFF path | What it does |
|---|---|---|
| `GET` | `/screens/orders` | The order list, with the item count and the formatted total (`$19.00`) |
| `GET` | `/screens/orders/{id}` | The order and the product suggestions from the catalog, in a single response |
| `POST` | `/actions/orders` | Creates an order: `{"customerName": "Ana"}` |
| `POST` | `/actions/orders/{id}/items` | Adds a catalog product: `{"productId": "...", "quantity": 2}` |
| `POST` | `/actions/orders/{id}/place` | Places the order |
| `GET` | `/health` | BFF health |

The BFF has no business rules. It looks up the product name and price in the catalog before adding the item, turns
API errors into messages for the screen (`{"message": "..."}`, with 400, 404, 422, or 502 when the API does not
answer) and passes on what the API decides, such as `canAddItems` and `canPlace`. In the web app, Vite forwards
`/screens` and `/actions` to the BFF, so the page and the BFF share the same origin, as in production.

## API

| Method | Path | What it does |
|---|---|---|
| `POST` | `/orders` | Creates an order: `{"customerName": "Ana"}` |
| `POST` | `/orders/{id}/items` | Adds an item: `{"productName": "Pen", "quantity": 2, "unitPrice": 3.5, "currency": "USD"}` |
| `POST` | `/orders/{id}/place` | Places the order |
| `GET` | `/orders/{id}` | One order |
| `GET` | `/orders?limit=50` | The most recent orders |
| `POST` | `/catalog/products` | Registers a product: `{"name": "Pen", "price": 3.5}` |
| `GET` | `/catalog/products` | The catalog, sorted by name |
| `GET` | `/catalog/products/{id}` | One product |
| `GET` | `/health` | API health |

Rules: an order starts as a draft and needs the customer name; the quantity is a whole number greater than zero; all
items use the same currency; only a draft with at least one item can be placed, and after that it no longer changes.
Violated rules answer 422, orders and products that do not exist, 404, and invalid bodies, 400, always as
`application/problem+json`. On the first start, the API registers three sample products if the catalog is empty.

| Folder | Contents | Depends on |
|---|---|---|
| `src/domain` | `Order`, `OrderItem`, `Money` and `CatalogProduct`, with the rules | nothing |
| `src/repositories` | The interfaces and the implementations in `memory/` and `postgres/` | domain |
| `src/services` | The use cases, which load, change and save | domain and the repository interfaces |
| `src/routes` | Fastify routes, schemas and the translation of errors into problem JSON | services, domain |

## Architecture

`test/architecture.test.ts`, at the root, ensures the programs only talk over HTTP: the web app imports nothing from
the API or the BFF and only calls `/screens` and `/actions`, the BFF imports nothing from the API, and the API does not
know the BFF and the web app exist. Each program has its own types for the contract it consumes. In the API,
`test/layering.test.ts` enforces the direction of the layers.

## Persistence

PostgreSQL with `pg`, read from `DATABASE_URL`. `romanctl up sample-app` creates the `sample_app` database and writes
the variable to the root `.env`, which the API reads. The tables are created on startup with
`CREATE TABLE IF NOT EXISTS`, under `pg_advisory_xact_lock`, which does not evolve the schema: adopt migrations before
you have data that matters.

The HTTP tests use the in-memory repositories. The PostgreSQL repository test only runs with `DATABASE_URL`.

## Tests

| Program | What the tests cover |
|---|---|
| api | Domain, services, HTTP with `inject` and, with `DATABASE_URL`, the PostgreSQL repositories |
| bff | Screens and actions against a fake API on a real HTTP server: the join, the product lookup and the error translation |
| web | Pages with Testing Library and jsdom, with a mocked `fetch` |

## Publish

`romanctl publish` generates a single `Dockerfile`, with the `APP` argument (`api` or `bff`), and a `compose.yaml` with
both services. The BFF image carries the compiled web app and serves it on the same port, from `WEB_DIST`, so in
production there are two containers: the API, which only the BFF sees, and the BFF, published on port 3301.

```bash
DATABASE_URL=postgres://user:password@db:5432/sample_app docker compose up --build
```
